# Accounts and login options (2026-11-25)

Research for step 1 of [social-identity](../../planning/issues/social-identity.md):
how players log in, at what cost, with what lock-in, what we would store, and
what it adds to the single-host deployment in `deploy/`. The decision is
proposed in [ADR 0055](../decisions/0055-accounts-oauth-login-in-arena-door.md).

Prices come from vendors' pages as summarized by 2026 third-party pricing
guides. The vendor pages were not opened directly here, so check them before
spending money. Scale assumptions: **playtests** mean tens of players a month;
**modest growth** means a few thousand.

## What the game needs

- An account id that `arena-door` can put into signed match tickets. The match
  server already trusts only tickets (ADR 0045), so login stays out of
  `arena-sim` and the match protocol.
- A stable key for the `Name#1234` handle, friends and the admin role, and as
  little else as possible: no email, no password, no real name. A provider
  subject id tied to a handle is still personal data, so even the minimum
  needs a privacy notice.
- Guests keep playing without an account.
- Account deletion that the operator can carry out completely.
- At most one more small process, ideally none, on a host that also runs a
  30 Hz match loop.

## Options

| Option | Price at playtest scale | Price at a few thousand | Lock-in | We store | Deletion | Ops on our host |
| --- | --- | --- | --- | --- | --- | --- |
| **Own OAuth 2.0 / OIDC login** against Discord, Google, GitHub, with our own session cookie | $0 (providers charge nothing for login) | $0 | None: standard protocols, one provider row per account | provider + subject id, handle, timestamps | delete our row; the provider keeps its own account | no extra process: code in `arena-door`, one SQLite file on a volume; an OAuth app per provider, and a published Google app audience |
| **WorkOS AuthKit** | $0 (first 1M MAU free) | $0 | Medium: hosted login UI and user store, export needed to leave | WorkOS user id (+ whatever WorkOS keeps) | API call + our row | none; outbound HTTPS |
| **Clerk** | $0 (50k monthly retained users free since Feb 2026) | $0 | High: SDKs centred on React/Next; session model is Clerk's | Clerk user id | API + our row | none; JS SDK in the page |
| **Supabase Auth** | $0 (50k MAU) | $0, but free projects pause after a week without activity; Pro $25/mo | Medium: Postgres-backed, exportable | Supabase user id | API + our row | none, but a paused project blocks all logins |
| **Auth0** | $0 (25k MAU on Free; MFA and roles limited, 1-day logs) | $0, paid from $35/mo | Medium-high: rules/actions and hosted UI | Auth0 user id | API + our row | none |
| **Ory Kratos** (self-hosted) | $0 | $0 | Low (open source) | identities in its database | its admin API | ~80 MB process (community report) + its database, and we build every login/recovery screen |
| **Keycloak** (self-hosted) | $0 | $0 | Low (open source) | users in its database | admin console/API | 0.5–2 GB JVM (community reports) next to the match loop, upgrades, its own admin surface |
| **Own passwords** | $0 | $0 | None | password hashes, emails | ours | password reset email, breach liability, credential stuffing defence |

### Notes

- **Social OAuth is free at any scale here, with minimal scopes.**
  - Discord's `identify` scope returns the user id and username without an
    email, which suits a game.
  - Google's `openid` scope alone yields the permanent `sub`; `profile` would
    add a name and picture we do not want.
  - A GitHub OAuth app with no scopes can read the public user, whose numeric
    `id` is permanent (unlike the login name).
  - None of the three charges for login.
  - Discord's rate limits are dynamic and read from response headers. Login
    is a handful of calls per user, so they do not matter at our scale.
- **Provider setup has limits of its own.** A Google app in Testing mode
  allows at most 100 listed test users. Basic identity scopes such as
  `openid` are exempt from that allowlist, and publishing the app audience
  removes the limit. Consent screens show the app's privacy policy link. We
  did not check Discord's developer policy for a privacy-policy requirement;
  assume one is needed.
- **Hosted services are free at our scale too**, so they compete on lock-in and
  operations, not price. WorkOS has the most generous free tier (1M MAU) and
  bills only for enterprise SSO connections, which a game does not need.
  Clerk's free tier rose to 50k retained users in February 2026. Supabase's
  free projects pause after a week of inactivity, which would lock players out
  between playtests unless we pay $25/mo.
- **Self-hosted identity servers cost memory and work.** Keycloak needs
  roughly 0.5–2 GB of JVM memory by community reports, on the host whose
  bottleneck is the match loop. Kratos is light (about 80 MB) but API-only, so
  we would build and maintain every screen.
- **Passwords are not worth it.** A password store brings email delivery,
  reset flows, hashing parameters, breach exposure and credential-stuffing
  defence, all for players who almost all already have Discord, Google or
  GitHub. The issue asks not to build one unless research shows it is worth it;
  it does not.
- **Rust support for our own login.** The `openidconnect` (4.1.0) and `oauth2`
  (5.0.0) crates implement authorization code + PKCE, state and nonce checks,
  and ID token validation, though the flow is small enough to write against
  each provider's token and user endpoints directly. `rusqlite` (0.43.0) gives
  a one-file store on a Compose volume next to the single door instance (ADR
  0046 already made the door a single instance).

## Data we would keep (own OAuth)

Per account: our account id (random), provider name, the provider's
permanent subject id, the chosen handle and its number, created and
last-login times, and a session generation counter. The admin role comes
from deploy configuration on each request and is not stored. No email,
token or avatar is stored; access tokens are used once to read the subject
id and dropped. Sessions are signed `__Host-` cookies (`HttpOnly`, `Secure`,
`SameSite=Lax`) carrying the account id, generation and expiry. They are
verified with a key separate from `ARENA_TICKET_KEY` and checked against the
database on each use.

Deleting an account removes its row, its friend edges and its handle; the
provider's own account is untouched and the player can unlink the app there.

## Revision (2026-11-25): WorkOS AuthKit and PostgreSQL

The user then required login without a social account and PostgreSQL
storage, so [ADR 0055](../decisions/0055-accounts-oauth-login-in-arena-door.md)
moved to WorkOS AuthKit. WorkOS's pricing page and docs, read that day (no
"last updated" date shown):

**Pricing.**
- The first 1M monthly active users are free. "Monthly active" means anyone
  who signs up, signs in or updates their profile in a calendar month.
- Each further 1M costs $2,500/month. Whether partial blocks are prorated
  is not stated.
- Add-ons:

  | Add-on | Price |
  | --- | --- |
  | Custom domain | $99/month |
  | Radar | first 1,000 checks free, then $100/month per 50,000 |
  | SSO, Directory Sync | $125 per connection, falling with volume |
  | Audit log streaming | $125/month per connection |

- Staging environments are free; only production is billed.

**Login methods.**
- Email + password, emailed codes (magic auth), multi-factor login, social
  login and passkeys.
- Social providers listed: Google, Microsoft, GitHub, Apple, GitLab,
  LinkedIn and Slack. Discord is not mentioned.
- In staging, WorkOS's default Google and GitHub credentials need no OAuth
  apps.
- Passkeys work only in the hosted page, and WorkOS advises a custom domain
  before enabling them in production.

**API.**
- `GET /user_management/authorize` takes `provider=authkit`, state, and
  PKCE (S256), optionally with `screen_hint=sign-up`.
- `POST /user_management/authenticate` takes a JSON body with `client_id`,
  `client_secret` (the API key), `grant_type`, `code` and `code_verifier`.
  It answers with `user` and an `access_token` whose `sid` claim names the
  session.
- `GET /user_management/sessions/logout?session_id&return_to` ends the
  WorkOS session.
- `DELETE /user_management/users/{id}` takes a Bearer API key.
- Rate limits:
  - 6,000 requests per minute per key overall;
  - authenticate: 10 per minute per email;
  - hosted email sign-ins: 10 per minute per email and IP.

**Emails and leaving.**
- WorkOS sends verification, code and reset emails by default; we can opt
  out and send our own.
- Users export from the dashboard without password hashes. Hashes (bcrypt)
  come only through a support request.

**PostgreSQL over SQLite.** SQLite was enough for playtests. PostgreSQL
lets more than one door share the accounts, and matches the project's
plan to standardise on PostgreSQL, one database per kind of data.
