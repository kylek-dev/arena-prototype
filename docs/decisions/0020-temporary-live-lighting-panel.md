# ADR 0020: Temporary live lighting controls

Date: 2026-11-07. **Status: accepted for local prototype implementation**, requested by the user for art tuning. Human browser/rendered review remains pending.

## Decision

Add **Lighting tweaks (temporary)** to the game menu and a shortcut in Settings → Graphics. Open a movable nonmodal window without a scrim, using the existing `MovableWindow`/focus policy. Native range inputs own keyboard input while focused; clicking/refocusing the arena resumes gameplay with the panel still open. Closing/reopening retains values, Escape from a control closes the window, and Reset restores the starting values.

Ten session-only sliders cover background red/green/blue (0–1), ambient brightness (0–3000), main/fill illuminance (0–20000 lux), exposure (EV100 4–14), bloom intensity (0–1), threshold (0–5) and wide halo contribution (0–1). Values update during dragging without reload. Starting values match current art settings, including the user's manual change to EV100 **10.0**, which supersedes the earlier EV100 8.0 in ADR 0019. Do not silently restore the older value. Show readable numeric values and a selectable JSON block for copying successful settings before refresh. Do not persist experimental slider values or mix them into HUD profiles. The existing bloom enable toggle remains a labelled device setting; slider values remain available while bloom is disabled and are reapplied when enabled. Staff-local halos/sparks are not controlled by these bloom sliders.

A separate optional `arenaShell.readLighting()` presentation callback returns ten values in the documented catalog order: `[backgroundR, backgroundG, backgroundB, ambient, keyLight, fillLight, exposure, bloomIntensity, bloomThreshold, bloomSpread]`. JavaScript rejects non-finite updates and clamps supported values; Rust independently validates/clamps each entry, falling back to current defaults for missing/non-finite values. An older shell without this callback keeps current default lighting.

Tag only the two arena directional lights with explicit roles. Update existing clear-color/ambient resources and camera exposure/bloom uniforms in place, assigning only changed fields. Never change weapon spill lights, unrelated lights, camera transforms, imported assets, collision or combat. Chain this application after ordinary graphics preferences so adding/removing bloom cannot discard live slider values. No mesh/material rebuild, custom shader, new dependency, runtime AI, server authority or combat input ABI change is involved.

## Verification

### Expanded tuning controls (2026-11-08)

User feedback found brightness-only tuning either washed out or too dark. Extend this same temporary presentation panel with neutral-by-default Bevy 0.20.1 color grading: post-tonemap saturation, section-wide contrast/gamma, shadow lift, midtone/highlight gain, temperature and tint. Add RGB color and elevation/rotation for each tagged arena light, plus a tone-mapping selector (Reinhard, Reinhard luminance, ACES fitted). These three operators do not require LUT assets. Keep EV100 10.0, current light colors/directions and Reinhard as defaults; no new shadows, material edits, custom shaders or dependencies. Light direction changes only tagged light transforms, never camera/actor transforms.

Append, never reorder, the callback: indices 10–28 are `[saturation, contrast, gamma, shadows, midtones, highlights, temperature, tint, keyR, keyG, keyB, fillR, fillG, fillB, keyPitch, keyYaw, fillPitch, fillYaw, tonemapping]`. Pitch/yaw are degrees (positive pitch means downward elevation); tone-mapping values are 0/1/2, rounded and clamped. Missing appended fields remain neutral/current defaults, including for older ten-value shells. Both boundaries validate independently. Group controls visually without changing callback order. Keep Reset, session-only lifetime and JSON export; grade only the rendered world, not the HTML HUD. Explain bloom-first isolation and separate shadow/highlight tuning. Human rendered review of the extension is pending.
