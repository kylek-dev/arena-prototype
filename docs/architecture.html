Arena Prototype / Repo guide

Rules at the core.
Browser on the outside.

The browser collects your actions. Rust decides what happens. Bevy draws the result. Keeping these separate makes the game easier to test and prepares it for a future server.

Today: local practice against a stationary opponent · No multiplayer

One action through the game

01 / Input

You press a key

JavaScript tracks keys and mouse gestures. A narrow JS/WebAssembly bridge passes intent to Rust.

→
02 / Rules

The simulation decides

At 30 ticks per second, Rust checks movement, collisions, attack range, line of sight, health, and cooldowns.

→
03 / Presentation

You see the result

Bevy updates the 3D scene and smooths movement between ticks. JavaScript updates the HTML HUD.

All of this currently runs locally in your browser. WebAssembly is compiled Rust running inside the page—not a backend service.

Where things live

crates/arena-sim/
The rulebook. Pure Rust with no graphics, browser, network, or OS clock. The original 1D duel lives in src/lib.rs; the browser’s planar arena rules live in src/arena.rs.
crates/arena-client/
The visual adapter. Bevy owns the camera, 3D objects, and rendering. It samples browser controls, steps the shared simulation, and publishes state for the HUD. Browser graphics use WebGL2.
web/
The browser shell. HTML/CSS provide the page and HUD. input.js is a testable input state machine; shell.js connects DOM events, focus, cursor capture, loading, and HUD updates.
crates/arena-headless/
The no-window runner. Sends scripted commands to the original duel and prints tick-tagged events. Exercises shared rules without a browser or renderer.
tests/ + scripts/
The safety net and tooling. Node unit tests cover input; Rust tests cover rules and replay consistency. Scripts handle checks and web builds. Browser diagnostics are optional; rendered review is manual.
assets/
Presentation content. Character assets and provenance records. Model geometry does not determine collision or combat outcomes.
docs/ + planning/
The reasoning and roadmap. Architecture notes, numbered decision records, developer guides, research, and future work.

The important boundary

Implemented: independent rules

  • Callers supply commands and advance ticks explicitly.
  • Integer simulation state keeps rule results repeatable.
  • Commands resolve in supplied order—not simultaneously.
  • Rendering and character models do not decide damage.

Planned: server authority

Browser intent → server validation → shared rules → authoritative state back to the browser.

The server would verify identity and commands, rather than trust client health, damage, or positions. Networking, server validation, durable replay files, and persistence are not implemented.
